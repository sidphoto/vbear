# 0006 幕僚長是 VBear 內建的角色，派工走員工的聊天，這版只做「自己動手」第 1、2 項

日期：2026-11-07　狀態：已決定（使用者授權「細節依決策紀錄決定」，依 ADR 0001–0005 與 GLOSSARY 提出；第 2、4、6 點是使用者可以再改的取捨，改的話要連同畫面文字與 `docs/SECURITY-MODEL.md` 一起改）

## 背景

路線圖第 4 項 v0.15.0「幕僚長派工」：用的人跟 CEO 聊想做什麼，幕僚長提議要哪些員工、怎麼分工、第一件工作，用的人確認後
VBear 建員工、派工，並用「AI 自己做了什麼」清單讓用的人看到每一步（ADR 0003）。

GLOSSARY 已經定了：CEO 是用的人第一張角色卡（職位 CEO），只聊天；幕僚長是「替用的人規劃要哪些員工、怎麼分工的 AI 角色；
預設只提議」。ADR 0003 定了五個「自己動手」勾選項（預設都不勾）與三件永遠不准做的事。

VBear 到 v0.13.0 已經有：

- 組隊會議（`staffing.py`、`staffing_runner.py`，P35）：對一張任務卡，幾位幕僚各發言一次，再由 CEO 職位的卡寫組隊提案；
  採用要用的人自己做六步（啟用、用精靈建卡、插技能、帶到任務卡的隊伍、帶去開會、記下採用），提案本身什麼都不做。
- 會議的引擎（`board_engine.HeadlessBoard`）：沒有工具的 headless Claude Code 呼叫、`--json-schema` 結構化輸出、每次檢查 init 事件
  只有 StructuredOutput、沒有 MCP，每次呼叫有花費上限，和會議、組隊、聊天共用每天上限。
- 流程（`flows.py`、`flow_executor.py`、`runner.py`）：任務卡的隊伍、Claude Code 串流執行者、Codex 審查、合併關卡、自動模式。
  要 git 工作目錄、風險接受（Claude 與 Codex 兩個登入的指紋）、執行者固定是 Claude Code，不看角色卡的工具。
- 和角色卡聊天（P36、P38）：Claude Code 與 Codex，每張卡自己的工作資料夾，每個指令、每個檔案修改都問，每回合有上限、計入每天上限。

## 決定

1. **幕僚長是 VBear 內建的角色，不是角色卡，也不是 CEO 自己的能力。** 用的人在 CEO 的聊天頁按「請幕僚長安排」，
   VBear 用固定的指示（寫在程式裡，用的人不能改）做一次沒有工具的 headless Claude Code 呼叫（會議引擎），
   讀「你和 CEO 最近的對話」與「能聊天的員工清單」當資料，輸出一份結構化的提議。理由：
   - GLOSSARY 把 CEO 寫成「一張普通的角色卡」、幕僚長寫成「AI 角色」，兩者分開；派工要的規則（只能指清單上的員工、
     不能出現上限、完整模式、技能安裝）應該是 VBear 固定的，不能被一張可以改指示的卡蓋掉。
   - 不用多建一張卡（ADR 0001：像 Grok Bot 一樣簡單），也不會在聯絡人、大廳多出一個不能聊天的「員工」。
   - 結構化提議走已經在用、每次都檢查「沒有工具」的會議引擎；CEO 的聊天是有工具、會跳允許卡的互動程序，要在裡面產生
     可驗證的提議，只能解析自由文字，而且 Codex 的 CEO 根本不走這個引擎。
   - 代價：幕僚長目前需要 Claude Code（ADR 0001 Q1-5 的做法：只有 Codex 的人看到「幕僚長目前需要 Claude Code」與取得方法）。
     CEO 是 Codex 卡時，和 CEO 的對話會送給 Claude（按鈕旁寫明）。
2. **派工走員工的聊天。** 確認之後，VBear 建好新員工（安全模式）與一張任務卡，再照順序在每位員工的新聊天裡送出那一步的訊息；
   下一步等上一步的回合正常結束才送，並附上上一步員工的最後回覆（標成資料）。員工照舊每個指令、每個檔案修改都要用的人按允許。
   不用流程（git、風險接受、Codex 審查、合併關卡）：對沒打開過終端機的人太重，而且流程的執行者不看角色卡的工具。
3. **確認一次就做完整份計畫。** 提議卡列出每一步交給誰、送什麼字、最多花多少；用的人可以改字、刪步驟、換人、改新員工的名字與模型，
   按「確認派工」後 VBear 照順序做完，中途不再逐步確認。用的人隨時可以停止。
4. **「自己動手」這版做第 1、2 項，預設都不勾**：
   - 第 1 項「幕僚長可以自己建新員工」：提議一到，新員工直接建好（安全模式、VBear 固定的職位指示），不必按確認。
   - 第 2 項「幕僚長可以自己派工給員工」：提議一到，就照提議開始派工，不必按確認；但提議裡要的新員工還不存在（沒勾第 1 項）、
     VBear 拿掉或標出了任何東西、或幕僚長有問題要問你，就照舊停在提議卡等你確認。
   - 第 3、5 項（例行工作、倒數接續）跟著 v0.18.0 的例行工作做；第 4 項（安全模式裡不必每次問）不在這版，聊天照舊每次都問。
   - 設定頁只列這版真的有作用的兩項，另寫一句「其他三項會在之後的版本加入」，不放不能用的勾選框。
5. **三件永遠不准做的事，由程式的結構擋，不靠提示詞**：
   - 提議的格式沒有任何上限、模式、技能、網址欄位（`additionalProperties: false`，多出的欄位整份作廢）。
   - 幕僚長與派工的程式不寫 `config.json`、不啟動終端機或完整模式、不裝技能：測試掃描這些模組的匯入與呼叫，並在跑完一整次派工後
     確認 `config.json` 一個位元組都沒變。派工只透過聊天服務送訊息，新員工一律 `launch_mode: "safe"`。
   - 「自己動手」的勾選只能由用的人在設定頁改（瀏覽器的 POST，帶 `X-VBear`），提議與派工改不到。
6. **花費**：幕僚長每次最多 US$0.30（再受今天剩下的限制），計入每天上限，和會議、組隊、聊天共用一天。
   派工每一步是員工聊天的一個回合，照聊天每回合上限與每天上限；提議卡先寫「最多 US$（步數 × 每回合上限）」與今天還剩多少。
   碰到每天上限或方案用量上限時，派工暫停，寫明原因與什麼時候恢復（每天上限是本機明天 0 點；方案用量上限照 AI 工具說的，沒說就寫「未知」），
   由用的人按「繼續」。倒數與自動接續屬 v0.18.0（第 5 項）。
7. **「AI 自己做了什麼」清單列出派工的每一個動作**（建員工、建任務卡、送出第幾步、暫停、繼續、停止、撤回），每筆寫明是誰決定的：
   「你確認的」或「自己動手第 1／2 項」。可以停止進行中的派工；VBear 建的員工可以撤回（停用，不刪，聊天紀錄保留）。
   已經送出的訊息收不回，清單照實寫。

8. **暫停時說清楚，「繼續」只由用的人按。** 暫停的說明寫明是哪一步、哪個 AI 工具、每天上限是多少、什麼時候恢復
   （每天上限是本機明天 0 點；AI 工具說了恢復時間就寫那個時間，沒說就寫「未知」）。VBear 不倒數、不自動繼續（那是 v0.18.0）。
   按「繼續」時，已經送出但沒正常結束的那一步**不會重做**，直接做下一步（下一步會收到「上一步沒有正常做完，回覆可能不完整」）；
   提議卡與派工頁都要把這件事寫在按鈕旁邊。要重做那一步，請另開一份派工。
9. **畫面只用平白的話，不用內部代碼。** 提議卡、派工頁、「AI 自己做了什麼」都把錯誤代碼（例如 `empty_plan`）、
   暫停原因、是誰決定的（你、自己動手第 1 項、第 2 項、VBear）換成一句白話；CEO 是 Codex 卡時，按鈕旁寫明這段對話會送給 Claude Code。

## 考慮過的其他選項

- **幕僚長是另一張角色卡（職位「幕僚長」）**：可以換工具與模型，但用的人要多建、多管一張卡，卡的指示可以改到 VBear 的固定規則；
  它不能聊天，放在聯絡人裡會讓人困惑。不選。
- **幕僚長是 CEO 自己的能力（在 CEO 的聊天裡直接提議）**：最像 Grok Bot，但提議要從聊天的自由文字裡解析，CEO 程序有工具、
  會跳允許卡，Codex 的 CEO 也做不到同一套檢查。不選。CEO 照 GLOSSARY 只聊天。
- **派工走流程（任務卡的隊伍＋執行者＋審查）**：已經有自動模式與審查，但要 git 工作目錄、兩個 AI 工具的登入指紋、風險接受，
  執行者固定是 Claude Code。對 ADR 0001 的對象太重。不選；之後可以讓一步變成一個流程。
- **每一步都要按確認**：最保守，但五步的工作要按五次，和「確認一次」的提議卡重複；自己動手第 2 項也就沒有意義。不選。
- **沿用組隊會議（幾位幕僚發言，再由 CEO 寫提案）**：一次要好幾個呼叫，花費與等待都多；而且要先有任務卡。不選；組隊會議照舊保留。

## 後果

- CEO 的聊天頁多一個「請幕僚長安排」；只有 Codex 的人看到「目前需要 Claude Code」。
- 新的紀錄：`<state>/chief/`（幕僚長的每次提議，會議引擎的格式）、`<state>/dispatch/`（派工）。兩者都計入或關聯到每天上限的帳。
- 員工之間只靠文字交接：員工 B 看不到員工 A 工作資料夾裡的檔案（共用資料夾是 v0.17.0）。
- 上一步員工的回覆會自動成為下一步的輸入（標成資料，不是指令）。若上一步的回覆被惡意內容影響，下一步的員工可能被帶偏；
  員工每個指令仍要你按允許，這是殘餘風險，寫進 SECURITY-MODEL。
- 殘餘風險（既有，照實寫）：員工被允許的指令可以讀到 VBear 的存取權杖並呼叫 VBear 自己的 API（例如改上限）；VBear 只能保證
  自己的幕僚長與派工程式不做這三件事，擋不了用的人親手允許的指令。
- 幕僚長讀「你和 CEO 最近的對話」並送給 Anthropic（按鈕和對話框都寫明）；這是一條新的對外資料路徑，和會議、組隊同一類，用的是你自己的 Claude Code 與方案。
- 回到沒有派工的版本（v0.13.0；v0.14 沒有發行）時，派工與幕僚長的紀錄留在原處、不被讀，VBear 建的員工和任務卡照舊是普通的卡；見 CHANGELOG。
